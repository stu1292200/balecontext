## 3. How the middleware chain is built: `load_middleware` (`base.py:27-104`)

**Per-layer behavior:** `convert_exception_to_response` (`django/core/handlers/exception.py:25-61`) catches any exception from the inner layer and converts it with `response_for_exception` (`54-58`). `MiddlewareMixin.__call__` (`django/middleware/__init__.py:35-45`) does this:
1. It calls `process_request` (`40-41`).
2. If that returns nothing, it calls `self.get_response(request)` (`42`), which is the next layer inward.
3. It calls `process_response` (`43-44`).

So the request passes inward through the layers, and the response passes back outward through the same layers.

# How `{% extends %}` and `{% block %}` are rendered

This is based on the BaleContext excerpts. I didn't open the files myself, and I changed nothing. All paths are under `django/template/`.

## 1. Compile time: building the nodes (`loader_tags.py`)

**`do_block`** (214-243) builds a `BlockNode`:
- It requires exactly one argument, the block name (221-224).
- It rejects a duplicate block name within one template by checking `parser.__loaded_blocks` (227-234).
- It parses the body up to `endblock` (235) and accepts either `endblock` or `endblock <name>` (238-241).
- It returns `BlockNode(block_name, nodelist)` (243).

**`do_extends`** (291-312) builds an `ExtendsNode`:
- It requires one argument (302-304).
- It resolves relative paths with `construct_relative_path` (305), compiles the parent name as a filter expression (306), and parses the rest of the template (307).
- It raises if a second `extends` is found (308-311).
- It returns `ExtendsNode(nodelist, parent_name)` (312).

**`ExtendsNode.__init__`** (90-94) records the child's own blocks: `self.blocks = {n.name: n for n in nodelist.get_nodes_by_type(BlockNode)}` (94). `NodeList.get_nodes_by_type` (`base.py:1110-1115`) collects nodes recursively.

## 2. Render time: `ExtendsNode.render` (`loader_tags.py:134-160`)
1. **135:** `get_parent(context)` (117-132):
   - It resolves `parent_name` and raises `TemplateSyntaxError` if it is empty (118-125).
   - A `Template` object, or a backend template that wraps one, is used directly (126-131).
   - Otherwise it calls `find_template` (132).
2. **`find_template`** (99-115) keeps a history of origins in `render_context` (106-109) and passes it as `skip=` to `Engine.find_template` (`engine.py:155-163`). That function tries each loader (157-160) and raises `TemplateDoesNotExist` with the combined `tried` list (163). The `skip` list is what lets a template extend another template with the same name, such as an overridden admin template, without finding itself again.
3. **137-139:** it creates a `BlockContext` (`BlockContext.__init__`, 15-17, a `defaultdict(list)` of per-name queues) in `render_context` if one isn't there yet.
4. **142:** `block_context.add_blocks(self.blocks)` adds this template's blocks. `add_blocks` (22-24) does `insert(0, block)`, so the most recently added blocks go to the front of each queue.
5. **144-155:** it finds the first non-text node of the parent. If that node is not an `ExtendsNode`, the parent is the root. All the parent's `BlockNode`s are then added to the context (150-154).
6. **159-160:** it renders the parent. `push_state(compiled_parent, isolated_context=False)` (`context.py:210-221`) swaps `render_context.template`, and it skips `push()`/`pop()` of the context stack because of the `False` argument. Then `compiled_parent._render(context)` runs (`base.py:166-167`, `self.nodelist.render(context)`). It calls `_render` directly so the parser context stays the same (157-158).

For a chain of templates, each `ExtendsNode.render` adds its blocks and then renders its parent. The root template is the last one to add blocks, and `insert(0, ...)` puts its blocks first in each queue.

## 3. Rendering a block: `BlockNode.render` (`loader_tags.py:51-69`)
Rendering the root template reaches each `{% block %}`:
- **52:** it fetches the `BlockContext` from `render_context` (`RenderContext.get`, `context.py:204-205`).
- **53:** it pushes a new context layer: `with context.push():`.
- **54-56:** with no `BlockContext` (the template was rendered without inheritance), it renders its own body with `context["block"] = self`.
- **58:** otherwise `block_context.pop(self.name)` takes the last item in the queue (`BlockContext.pop`, 26-30). That item is the most-derived override. It returns `None` if the queue is empty.
- **59-60:** if nothing was found, it uses `self`.
- **63-65:** it builds a fresh `BlockNode` copy, so the stored `context` is not shared between threads. It sets `block.context = context` and `context["block"] = block`.
- **66:** `block.nodelist.render(context)` renders the chosen body. `NodeList.render` (`base.py:1107-1108`) joins the output of each node into a `SafeString`.
- **67-68:** it pushes the popped block back (`BlockContext.push`, 32-33), so the block can be rendered again, for example in a loop.

## 4. `{{ block.super }}` (`BlockNode.super`, `loader_tags.py:71-83`)
- Without a `context` attribute it raises `TemplateSyntaxError`. This happens if `block.super` is used in a base template (72-76).
- If the block context still holds a block with this name, `self.render(self.context)` renders it (78-82). Because the child's block was popped during `render` (58), the block that is rendered here is the next one up the chain, i.e. the parent's version.
- Otherwise it returns `""` (83).

## Summary
```
compile:  do_extends → ExtendsNode(nodelist, parent_name)   [self.blocks = child's blocks]
          do_block   → BlockNode(name, nodelist)
render:   ExtendsNode.render
            → get_parent → find_template (loader skip history)
            → BlockContext.add_blocks(child blocks)  (+ root's blocks if parent is root)
            → compiled_parent._render(context)
                → BlockNode.render: pop most-derived block → render its nodelist → push back
                   └ {{ block.super }} → BlockNode.super → renders the next block in the queue
```

I didn't see `BlockContext.get_block` (it's referenced at line 80 but its body wasn't in the evidence), so I'm inferring from its name that it peeks at the queue without popping.

# How Django renders `{% extends %}` and `{% block %}`

Paths are relative to the repo root. Almost everything is in `django/template/loader_tags.py`. I only read files and changed nothing.

## 1. Compile time (parsing)

**`{% block name %}` → `do_block`** (`loader_tags.py:214-243`)
- `:221-224` Requires exactly one argument, the block name.
- `:227-234` Duplicate names are caught with a per-parser list kept as `parser.__loaded_blocks`. A repeated name raises `TemplateSyntaxError`.
- `:235` `parser.parse(("endblock",))` compiles the body into a `NodeList`.
- `:237-241` Accepts `endblock` or `endblock <name>`.
- `:243` Returns `BlockNode(block_name, nodelist)`.

**`{% extends "base.html" %}` → `do_extends`** (`loader_tags.py:291-312`)
- `:302-304` Requires exactly one argument.
- `:305` `construct_relative_path` (`:246-288`) resolves `./` and `../` names against `parser.origin.template_name`. It rejects paths that escape the hierarchy (`:274-278`) and paths that point back at the same template (`:279-284`).
- `:306` The parent name is compiled as a `FilterExpression`, so it can be a literal or a variable.
- `:307` `parser.parse()` with no end tag consumes the rest of the template as the child's nodelist.
- `:308-311` A second `ExtendsNode` raises an error.
- `:312` Returns `ExtendsNode(nodelist, parent_name)`.

**Ordering rule.**
- `ExtendsNode.must_be_first = True` (`:87`).
- `Parser.extend_nodelist` (`django/template/base.py:618-635`) raises "must be the first tag" if a non-text node already exists (`:620-628`). Text nodes before it are allowed.
- `Parser.parse` (`base.py:530-609`) is the loop that calls each tag's compile function (`:601`) and adds the result to the nodelist (`:604`).

**Block index.**
- `ExtendsNode.__init__` (`:90-94`) builds `self.blocks = {name: BlockNode}` with `nodelist.get_nodes_by_type(BlockNode)`.
- This is a pre-computed index of every block the child defines, including nested ones.

## 2. Render time

### Entry
`Template.render` (`base.py:169-177`) does the following:
- `:171` It calls `render_context.push_state(self)`, which gives a fresh scope.
- `:173-175` It binds the template if the context has none yet.
- `:177` `_render` (`:166-167`) runs `self.nodelist.render(context)`.

A child template's nodelist is essentially one `ExtendsNode`, so rendering starts at `ExtendsNode.render`.

### `ExtendsNode.render` (`loader_tags.py:134-160`)
1. `:135` `get_parent(context)` (`:117-132`):
   - It resolves `parent_name` against the context.
   - An empty value raises an error (`:119-125`).
   - A `Template` object is used directly (`:126-128`), as is a backend wrapper (`:129-131`).
   - A string goes through `find_template` (`:99-115`).
2. `find_template` (`:99-115`) keeps a history of origins in `render_context["extends_context"]`, seeded with the current origin (`:106-109`). It passes that history as `skip=` to `engine.find_template` (`:110-113`). That is how recursive extends of the same name, like an `admin/base.html` that extends `admin/base.html`, load the next template with that name rather than looping.
3. `:137-139` Creates a `BlockContext` in `render_context` if one isn't there yet.
4. `:142` `block_context.add_blocks(self.blocks)` adds this template's blocks.
5. `:146-155` If the parent isn't itself an `ExtendsNode`, it is the root, so its blocks are added too. The check looks at the first non-text node.
6. `:159-160` Renders the parent through `compiled_parent._render(context)`. This calls `_render` directly, not `render`, so the parser context stays the same. `push_state(..., isolated_context=False)` keeps the same render-context scope, so the `BlockContext` stays visible.

### `BlockContext` (`loader_tags.py:14-39`)
This is a dictionary of lists, one list per block name, used as a stack.
- `add_blocks` (`:22-24`) does `insert(0, block)`, so each call puts its blocks at the front of the list.
  - The child is added first, then its parent, and so on up to the root.
  - The most-derived override therefore ends up last in the list, and the root's version first.
- `pop` (`:26-30`) takes from the end, which gives the most-derived override.
- `get_block` (`:35-39`) peeks at the end without removing it.
- `push` (`:32-33`) appends.

### `BlockNode.render` (`loader_tags.py:51-69`)
- `:52` Reads the `BlockContext` from the render context.
- `:53` Opens `context.push()`, so block-local variables like `block` are scoped.
- `:54-56` **No `BlockContext`:** the template is being rendered on its own, with no extends. It sets `context["block"] = self` and renders its own nodelist.
- `:57-68` **With a `BlockContext`:**
  - `:58` `block = block_context.pop(self.name)` takes the most-derived override.
  - `:59-60` If there is none, it falls back to itself.
  - `:63-65` It makes a fresh `BlockNode` copy and stores `context` on it. The copy keeps the original node from being mutated across requests or threads, as the comment on `:61-62` says. It sets `context["block"]` to the copy.
  - `:66` Renders the copy's nodelist.
  - `:67-68` Pushes the popped block back, so the same block name can render again, for example inside a loop or a second render.

### `{{ block.super }}` (`BlockNode.super`, `loader_tags.py:71-83`)
- `block` in the context is the copy from `render`, so `{{ block.super }}` calls this method.
- `:72-76` Raises `TemplateSyntaxError` if `context` was never set, which is the case when used in a base template.
- `:78-82` If another block with the same name is still on the stack (`get_block` is not `None`), it returns `mark_safe(self.render(self.context))`.
  - Because the child's block was popped, this render pops the next one up the chain, the parent's version.
  - That recursion walks up the inheritance chain.
- `:83` Otherwise it returns `""`.

## Worked example
With `base.html` containing `{% block content %}B{% endblock %}`, and `child.html` containing `{% extends "base.html" %}{% block content %}C{{ block.super }}{% endblock %}`:
1. `child.render` runs `ExtendsNode.render`. `add_blocks` puts the child's `content` in the list. The root check at `:146-155` finds `base.html` has no extends, so it adds the base's `content` at index 0, giving `[base, child]`.
2. The parent renders. Its `BlockNode.render` pops the child's block, so `C` renders.
3. `block.super` calls `self.render` again. `get_block` sees the base block, `pop` returns it, and `B` renders.
4. The block that was popped is pushed back each time (`:67-68`).

Result: `CB`.
