## Answer: run2-hook.followup1.answer.md

`Session.send()` hands redirect handling to `resolve_redirects`, and it reads the response body at two points. Everything below comes from the excerpts already in this conversation (`src/requests/sessions.py` unless noted), and I didn't modify any files.

## Redirect handling in `send()` (`sessions.py:773-824`)

1. **Initial send.** `allow_redirects` is popped from kwargs and defaults to `True` (`:773`). The first hop goes through `adapter.send` (`:784`), and then the response hooks and cookie extraction run (`:791-799`).
2. **Redirects followed (`:802-805`).** `send()` calls `self.resolve_redirects(r, request, **kwargs)` and consumes the whole generator into `history`.
3. **Folding the history (`:810-815`).** If there was any history, `r` is inserted at the front (`:812`). The last response is then popped off and becomes the returned `r` (`:814`). The remaining responses become `r.history` (`:815`).
4. **Redirects not followed (`:818-824`).** `send()` calls `resolve_redirects` with `yield_requests=True` and takes only the first item. That item is the next `PreparedRequest`, which it stores in `r._next`, so `Response.next()` can use it later. If there is no redirect, `StopIteration` is swallowed.

## Inside `resolve_redirects` (`:186-307`)

- **Detecting a redirect.** `get_redirect_target` (`:134-152`) returns a URL only if `resp.is_redirect` is true. It takes the `Location` header, re-encodes it from latin1, and decodes it as UTF-8 (`:142-151`). The loop runs while `url` is truthy (`:204`).
- **Per hop (`:205-273`):**
  - It copies the request (`:205`).
  - It records history (`:208-209`).
  - It raises `TooManyRedirects` once `len(resp.history) >= max_redirects` (`:216-219`).
  - It builds the new URL: scheme-relative `//` handling, fragment carry-over, and `urljoin` plus `requote_uri` for relative `Location` values (`:225-245`).
  - It calls `rebuild_method` (`:247`).
  - For any status other than 307 or 308, it drops `Content-Length`, `Content-Type` and `Transfer-Encoding` and clears the body (`:250-258`).
  - It removes the old `Cookie` header and re-prepares cookies from the response and session jars (`:261-269`).
  - It rebuilds proxies and auth (`:272-273`).
  - It rewinds a file-like body if it is rewindable (`:278-284`).
- **Sending the next hop (`:289-307`).** With `yield_requests` it yields the prepared request and stops. Otherwise it calls `self.send(...)` with `allow_redirects=False` (`:292-300`). So each hop re-enters `send()` but does not recurse into redirect handling. The loop owns the chain. It then stores cookies (`:303`), finds the next target (`:306`) and yields the response (`:307`).

## When the body is read

- **Adapter level: not read.** `HTTPAdapter.send` calls `urlopen` with `preload_content=False` and `decode_content=False` (`adapters.py:703-704`). `build_response` stores the urllib3 response as `response.raw` (`adapters.py:386`) without reading it.
- **Redirect hops: read.** Before following a redirect, `resolve_redirects` accesses `resp.content` to consume the socket (`:211-212`). If that raises `ChunkedEncodingError`, `ContentDecodingError` or `RuntimeError`, it falls back to `resp.raw.read(decode_content=False)` (`:213-214`). It then calls `resp.close()` to return the connection to the pool (`:221-222`). This happens even with `stream=True`.
- **Final response: only when not streaming.** At the end of `send()`, `if not stream: r.content` forces the full body to be read and cached (`:826-827`). With `stream=True` the body stays unread, so the caller must read or close it.
- **When `allow_redirects=False`.** The final response is the redirect response itself, and the same `if not stream` check applies (`:826-827`). The follow-up request is only prepared and stored in `r._next`, and no body is consumed for it.

I did not re-read `HTTPAdapter.send` or the `rebuild_*` helpers beyond the excerpts, so their internals aren't covered here.

## Answer: run2-hook.followup2.answer.md

Cookies are saved from the response into `self.cookies` (the session's jar) in `Session.send`. They are attached to the next request when it is prepared. I took this from the excerpts already in this conversation and didn't modify any files.

## Saving: response → session jar

1. **Per-response jar.** `Response.__init__` creates an empty `self.cookies` jar (`models.py:797-798`). `HTTPAdapter.build_response` fills it by calling `extract_cookies_to_jar(response.cookies, req, resp)` (`adapters.py:394-395`). This jar is what the caller sees as `r.cookies`.
2. **Extraction.** `extract_cookies_to_jar` (`cookies.py:135-150`):
   - It returns early if the urllib3 response has no `_original_response` (`:144-145`).
   - It wraps the request in a `MockRequest` (`:147`).
   - It wraps the raw `HTTPMessage` headers in a `MockResponse` (`:149`, `:114-126`). That gives `http.cookiejar` the interface it expects.
   - It calls `jar.extract_cookies(res, req)` (`:150`), which applies the stdlib's cookie policy.
3. **Into the session.** In `Session.send` (`sessions.py:793-799`):
   - Cookies from every response in `r.history` are extracted into `self.cookies` (`:794-797`). The history may come from hooks.
   - Cookies from the current response are extracted into `self.cookies` (`:799`).
   - This runs before redirects are resolved, so the first response's `Set-Cookie` is stored before the next hop.
4. **Redirect hops.** In `resolve_redirects`:
   - Cookies from the redirect response go into the new request's own jar (`sessions.py:266-267`). The code uses the old request `req` for this, because the copy has been mutated.
   - They are merged with the session jar (`:268`).
   - After each hop's `self.send`, cookies are extracted into `self.cookies` again (`:303`).

## Attaching: session jar → next request

1. **Merge at prepare time.** `Session.prepare_request` builds a fresh `RequestsCookieJar` and merges the session cookies into it. It then merges the per-request cookies on top (`sessions.py:531-533`, via `merge_cookies` at `cookies.py:604-625`). Passing `cookies=` therefore adds to the session jar and doesn't replace it. This merged jar is passed to `p.prepare(cookies=...)` (`sessions.py:552`).
2. **Where it runs.** `PreparedRequest.prepare` calls `prepare_cookies` after headers and before the body and auth (`models.py:443`).
3. **Building the header.** `prepare_cookies` (`models.py:699-720`):
   - It stores the jar as `self._cookies`, converting a dict with `cookiejar_from_dict` if needed (`:712-715`).
   - It calls `get_cookie_header(cookies_jar, self)` (`:718`).
   - It sets `self.headers["Cookie"]` if a header was produced (`:719-720`).
4. **How the header is computed.** `get_cookie_header` (`cookies.py:153-161`) wraps the request in a `MockRequest` (`:159`, `:45-49`). `MockRequest` records the scheme from the URL and keeps a `_new_headers` dict. The code calls `jar.add_cookie_header(r)`. The stdlib jar matches cookies by domain, path, secure flag and expiry, and writes a `Cookie` header into `_new_headers`. The function returns that header with `r.get_new_headers().get("Cookie")` (`:160-161`, `:98-99`).

## Redirect rebuild

On a redirect, `resolve_redirects` pops the copied `Cookie` header (`sessions.py:260-261`). It then calls `prepared_request.prepare_cookies(cookie_jar)` (`:269`) to compute a fresh header for the new URL. A cookie scoped to the original domain is therefore not sent to a different host.
