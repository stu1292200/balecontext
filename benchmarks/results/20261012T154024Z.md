## Redirect handling in `Session.send()` (`src/requests/sessions.py`)

**Setup**
- `send()` pops `allow_redirects` from kwargs, defaulting to `True` (`:773`). It keeps `stream` for later (`:774`).
- `adapter.send()` runs once (`:784`). The adapter never follows redirects itself, because `HTTPAdapter.send` passes `redirect=False` to urllib3 (`adapters.py:701`).
- After the hooks and cookie extraction (`:791-799`), the redirect step runs.

**If `allow_redirects` is true** (`:802-815`)
- `send()` creates the generator `self.resolve_redirects(r, request, **kwargs)` and drains it into a list: `history = [resp for resp in gen]` (`:804-805`).
- If any redirects happened (`:810-815`):
  - The original response `r` is inserted at the front of `history` (`:812`).
  - The last response is popped off and becomes the returned `r` (`:814`).
  - The remaining responses are stored in `r.history` (`:815`).

**Inside `resolve_redirects`** (`:186-307`)
- The loop runs while `get_redirect_target(resp)` returns a URL (`:202-204`). That method returns a target only if `resp.is_redirect` is true. It takes the `Location` header, re-encodes it as latin1, then decodes it as UTF-8 (`:142-152`).
- Each pass does the following:
  1. It copies the previous request (`:205`) and records the history (`:208-209`).
  2. It raises `TooManyRedirects` once `len(resp.history) >= self.max_redirects` (`:216-219`).
  3. It builds the new URL by handling `//` URLs and fragments, joining relative URLs and requoting (`:225-245`).
  4. It adjusts the method with `rebuild_method` (`:247`).
  5. For non-307/308 responses, it strips `Content-Length`, `Content-Type` and `Transfer-Encoding` (`:250-257`).
  6. It rebuilds cookies, proxies and auth (`:261-273`).
  7. It rewinds a file-like body if one exists (`:278-284`).
- Each hop is sent by a recursive `self.send(...)` call with `allow_redirects=False` (`:292-301`). That call forwards `stream`, `timeout`, `verify`, `cert` and `proxies`. Because of the `False`, each hop does not start its own redirect resolution.
- Cookies are extracted from each hop (`:303`). The next target is computed (`:306`) and the response is yielded (`:307`).

**If `allow_redirects` is false** (`:817-824`)
- `send()` does not follow anything.
- It calls `resolve_redirects(..., yield_requests=True)` and takes the first item. That is the next `PreparedRequest`, stored in `r._next` (`:820-822`). This is what `Response.next` exposes. If there is no redirect, `StopIteration` is swallowed (`:823-824`).

## When the body is read

There are three points where the body gets read:

1. **At the adapter, it is not read.** `urlopen` is called with `preload_content=False` and `decode_content=False` (`adapters.py:703-704`). `build_response` only wraps the urllib3 response as `response.raw` (`adapters.py:386`).
2. **For redirect responses, it is read inside the loop.** `resp.content` is accessed to "consume socket so it can be released" (`sessions.py:211-212`). If that raises `ChunkedEncodingError`, `ContentDecodingError` or `RuntimeError`, it falls back to `resp.raw.read(decode_content=False)` (`:213-214`). The connection is then released with `resp.close()` (`:222`).
   - This happens whether or not `stream=True`, so intermediate redirect bodies are always consumed. The final response is not covered by this loop.
3. **For the final response, it depends on `stream`.** `if not stream: r.content` (`sessions.py:826-827`) reads the whole body eagerly, after redirects are resolved. With `stream=True`, the body stays unread until the caller accesses `.content`, `iter_content()` or `.raw`.
   - The `stream` value used here comes from `kwargs.get("stream")` (`:774`). It was already merged from the per-call and session settings in `merge_environment_settings` (`:864`).

One consequence: with `allow_redirects=False`, the redirect response is returned with its body unread when `stream=True`. With `stream=False`, `r.content` is read at `:827`.

## Saving response cookies on the Session

1. **The jar lives on the session.** `Session.cookies` is the persistent jar. It is a `RequestsCookieJar`, and `prepare_request` and `send` both use it (`sessions.py:532`, `:799`).

2. **The adapter extracts cookies onto the `Response`.** `HTTPAdapter.build_response` calls `extract_cookies_to_jar(response.cookies, req, resp)` (`adapters.py:395`). The target is the new response's own `cookies` jar, created empty in `Response.__init__` (`models.py:798`).

3. **`extract_cookies_to_jar`** (`cookies.py:135-150`):
   - It returns early if the urllib3 response has no `_original_response` (`:144-145`).
   - Otherwise it wraps the request in a `MockRequest` (`:147`, `cookies.py:45-49`).
   - It wraps the response headers (`_original_response.msg`) in a `MockResponse` (`:149`, `cookies.py:121-126`).
   - It calls `jar.extract_cookies(res, req)` (`:150`). This is the stdlib `http.cookiejar` method, and it reads `Set-Cookie` headers through those mocks.

4. **`Session.send` copies them into the session jar** (`sessions.py:793-799`):
   - For any `r.history` created by hooks, each earlier response is extracted into `self.cookies` (`:794-797`).
   - Then `extract_cookies_to_jar(self.cookies, request, r.raw)` handles the response itself (`:799`).
   - This happens before redirects are resolved (`:802`), so the first response's cookies are saved even if it is a redirect.

5. **Each redirect hop does the same.** Cookies from the hop's response go into the session jar at `sessions.py:303`. They also go into the redirected request's own jar at `:266-267`, before `merge_cookies(cookie_jar, self.cookies)` at `:268`.

## Attaching cookies to the next request

1. **`Session.prepare_request`** (`sessions.py:524-533`) builds the cookies for the request:
   - Per-request cookies are converted to a `CookieJar` if they are a dict (`:527-528`).
   - It merges `self.cookies` and then the request cookies into a fresh `RequestsCookieJar` (`:531-533`).
   - `merge_cookies` (`cookies.py:604-625`) copies a `CookieJar` with `update` (`:619-620`) or per-cookie `set_cookie` (`:622-623`). A dict goes through `cookiejar_from_dict(..., overwrite=False)` (`:616-617`).
   - The request cookies are merged last, so they take effect on top of the session's.
   - The merged jar is passed to `p.prepare(cookies=merged_cookies)` (`:552`).

2. **`PreparedRequest.prepare`** calls `prepare_cookies(cookies)` (`models.py:443`).

3. **`prepare_cookies`** (`models.py:699-720`):
   - It stores the jar as `self._cookies` (`:712-715`).
   - It calls `get_cookie_header(jar, self)` (`:718`).
   - If that returns a header, it sets `self.headers["Cookie"]` (`:719-720`).

4. **`get_cookie_header`** (`cookies.py:153-161`):
   - It wraps the request in a `MockRequest` (`:159`).
   - It calls `jar.add_cookie_header(r)` (`:160`). The stdlib jar decides which cookies match the URL, domain, path and so on.
   - `MockRequest` collects the header it would add in `_new_headers` (`cookies.py:48`). `get_cookie_header` returns that value (`:161`, `get_new_headers` at `cookies.py:98-99`).

## Redirects

On a redirect, the old `Cookie` header is dropped (`sessions.py:261`). The jar is rebuilt from the redirect response and the session cookies (`:266-268`), then `prepared_request.prepare_cookies(cookie_jar)` regenerates the header for the new URL (`:269`).

## Answer: run2-hook.followup3.answer.md

Proxy choice happens in two stages: it first assembles a `proxies` dict from the call, the session and the environment. Then the adapter picks one entry from that dict for the URL.

## Stage 1: building the `proxies` dict

**In `Session.request`** (`sessions.py:639-643`), `proxies = proxies or {}`, then `merge_environment_settings` runs (`sessions.py:831-868`):
- If `trust_env` is set (`:845`), `no_proxy` is read from the per-call dict's `"no_proxy"` key (`:847`).
- `get_environ_proxies(url, no_proxy)` (`utils.py:873-882`) returns `{}` if `should_bypass_proxies` is true. Otherwise it returns `getproxies()`, which reads the `*_proxy` environment variables (and on Windows, the registry).
- Environment entries only fill gaps: `proxies.setdefault(k, v)` (`sessions.py:849-851`), so explicit per-call proxies win.
- Next, `merge_setting(proxies, self.proxies)` (`:863`) merges in `Session.proxies`. Per-call values override the session's (`:96-97`), and keys set to `None` are dropped (`:99-103`).

**In `Session.send`** (`sessions.py:762-763`), if `proxies` is not in kwargs, `resolve_proxies(request, self.proxies, self.trust_env)` (`utils.py:911-939`) runs. This is the path for a direct `send()` call, and it is also used on redirects:
- It copies the given proxies (`:930`).
- If `trust_env` is set and `should_bypass_proxies` is false (`:932`), it takes the environment proxy for the URL scheme, falling back to the `"all"` entry (`:935`).
- It adds that with `setdefault`, so existing entries win (`:937-938`).

Redirects use the same function through `rebuild_proxies` (`sessions.py:353`). The proxy is recomputed for each new URL, so `no_proxy` is re-evaluated per hop.

## How `no_proxy` is evaluated: `should_bypass_proxies` (`utils.py:810-870`)

- **Source:** the `no_proxy` argument is used if given (`:824`). Otherwise it reads the environment variable (`:825-826`). Lowercase `no_proxy` takes precedence over uppercase `NO_PROXY` (`:817-820`).
- **No hostname:** a URL with no hostname, such as `file:///`, always bypasses the proxy (`:830-832`).
- **Parsing:** the value is split on commas with spaces removed (`:837`).
- **IPv4 host** (`:839-847`): each entry is matched as a CIDR range (`is_valid_cidr`, `address_in_network`) or as an exact IP.
- **Hostname** (`:848-859`): the host is compared with and without the port, as an exact match or as a suffix. Leading dots are normalized, so `example.com` and `.example.com` both match subdomains.
- **Fallback:** if nothing matched, it calls the stdlib `proxy_bypass(hostname)` (`utils.py:137-146`) inside `set_environ("no_proxy", no_proxy_arg)` (`:861-865`). This covers platform-specific bypass lists, such as the Windows registry. A `TypeError` or `gaierror` counts as "do not bypass".

## Stage 2: picking the entry for the URL: `select_proxy` (`utils.py:885-908`)

It is called from `get_connection_with_tls_context` (`adapters.py:483`) and `request_url` (`adapters.py:583`).

- If the URL has no hostname, it returns `proxies[scheme]` or `proxies["all"]` (`utils.py:893-894`).
- Otherwise it takes the first key present in this order (`:896-906`):
  1. `scheme://hostname`
  2. `scheme`
  3. `all://hostname`
  4. `all`

So a host-specific entry beats a scheme entry, which beats the catch-all. Otherwise there is no proxy.

## Using the chosen proxy

- **Connection** (`adapters.py:483-510`): if a proxy was selected, `prepend_scheme_if_needed(proxy, "http")` adds a scheme when it is missing (`:493`). A URL with no host raises `InvalidProxyURL` (`:495-499`). The connection comes from `proxy_manager_for(proxy)` (`:500-503`). Without a proxy, it uses the plain `poolmanager` (`:506-507`).
