# What happens when `form.is_valid()` is called

## 1. Entry point: `is_valid()`
`django/forms/forms.py:204-206`
```python
return self.is_bound and not self.errors
```
- An unbound form short-circuits to `False`. No validation runs.
- Otherwise it reads the `errors` property.

## 2. Lazy trigger: `errors`
`django/forms/forms.py:197-202`

`errors` checks `self._errors is None`. If so, it calls `full_clean()` (line 201). Validation therefore runs once and is cached. Later `is_valid()` or `errors` calls reuse `_errors`.

## 3. Orchestrator: `full_clean()`
`django/forms/forms.py:324-339`

1. Creates an empty `ErrorDict` (line 328).
2. Returns early if the form is unbound (329-330).
3. Initializes `self.cleaned_data = {}` (331).
4. Returns early if `empty_permitted` is set and `has_changed()` is false (334-335). `has_changed()` is at 377-379 and uses `changed_data` at 381-383.
5. Runs three phases in order (337-339):
   - `_clean_fields()`
   - `_clean_form()`
   - `_post_clean()`

## 4. Phase 1: per-field validation, `_clean_fields()`
`django/forms/forms.py:341-350`

For each `(name, bf)` from `_bound_items()` (170-173):
1. `field._clean_bound_field(bf)` (345) is defined at `django/forms/fields.py:271-273`. It takes `bf.initial` if the field is disabled, otherwise `bf.data`, and calls `self.clean(value)`.
2. `Field.clean()` (`fields.py:203-211`) runs three steps:
   - `to_python(value)` (208, base impl at 182-183) coerces the raw value to a Python type. Subclasses override it.
   - `validate(value)` (209, base impl at 185-187) raises a `required` `ValidationError` if the value is empty and the field is required.
   - `run_validators(value)` (210, impl at 189-201) skips empty values. Otherwise it runs every validator in `self.validators` and collects all their `ValidationError`s instead of stopping at the first. Where an error code has a matching entry in the field's `error_messages`, the message is replaced (197-198). It then raises one combined `ValidationError` (200-201).
3. The result goes into `self.cleaned_data[name]` (345).
4. If the form defines a `clean_<name>()` method (346-348), it runs and its return value replaces the cleaned value.
5. Any `ValidationError` raised in steps 1-4 is caught (349) and passed to `add_error(name, e)` (350). Validation then continues with the next field, so errors from every field are collected.

## 5. Error handling: `add_error()`
`django/forms/forms.py:264-316`

- Non-`ValidationError` input is wrapped in one (282-285).
- If the error has an `error_dict`, `field` must be `None`, or it raises `TypeError` (287-294). Otherwise the error becomes `{field or NON_FIELD_ERRORS: error.error_list}` (296).
- For each target field (298-314):
  - It raises `ValueError` if the field isn't in `self.fields` and isn't `NON_FIELD_ERRORS` (300-304).
  - It lazily creates the error list in `self._errors`. Non-field errors get `error_class="nonfield"` (305-308). Field errors get the field's `auto_id` (310-313).
- The error list is extended (314), and the field is removed from `cleaned_data` (315-316). A field that failed validation therefore never appears in `cleaned_data`.

## 6. Phase 2: form-wide cleaning, `_clean_form()`
`django/forms/forms.py:352-359`

- It calls `self.clean()` (354). The base `clean()` (368-375) just returns `self.cleaned_data`. Subclasses override it for cross-field validation.
- A `ValidationError` is added as a non-field error with `add_error(None, e)` (355-356).
- If `clean()` returns something other than `None`, it replaces `self.cleaned_data` (357-359).

## 7. Phase 3: `_post_clean()`
`django/forms/forms.py:361-366`

It's a no-op hook in `BaseForm`. `ModelForm` overrides it in `django/forms/models.py:479-513`:
- `BaseModelForm.clean()` (`models.py:441-444`) sets `_validate_unique` and `_validate_constraints` to `True`.
- `_post_clean()` builds the model instance with `construct_instance` (496-498) and runs `instance.full_clean(...)` with `validate_unique=False` and `validate_constraints=False` (502-505). Errors from both go through `_update_errors` (500, 507).
- It then calls `validate_unique()` and `validate_constraints()` if enabled (510-513).

## 8. Result
Back in `is_valid()` (line 206), `not self.errors` is true only if `_errors` is an empty `ErrorDict`. That means no field errors and no non-field errors.

## Summary flow
```
is_valid() ─▶ is_bound? ─▶ errors ─▶ full_clean()
                                      ├─ _clean_fields(): Field.clean() [to_python → validate → run_validators] → clean_<name>()
                                      ├─ _clean_form():   clean()
                                      └─ _post_clean():   (ModelForm: model full_clean, unique, constraints)
          errors raised in any step ─▶ add_error() ─▶ _errors (and removed from cleaned_data)
```

# How `Field.clean()` runs validators and where the errors end up

## 1. `Field.clean()` runs three steps in order
`django/forms/fields.py:203-211`
```python
value = self.to_python(value)   # 208
self.validate(value)            # 209
self.run_validators(value)      # 210
return value                    # 211
```
Each step can raise a `ValidationError`, and the first one to raise stops the sequence. A `to_python` failure, for example, means `validate` and `run_validators` never run.

- **`to_python`** (`fields.py:182-183`) returns the value unchanged in the base class. Subclasses override it to coerce types, for example `CharField` (291-299) and `IntegerField` (335-350).
- **`validate`** (`fields.py:185-187`) raises `ValidationError(self.error_messages["required"], code="required")` if the value is in `empty_values` and the field is required.

## 2. `run_validators()` collects errors
`django/forms/fields.py:189-201`

1. It returns immediately for empty values (190-191). A non-required blank field skips validators.
2. It loops over `self.validators` and calls each one as `v(value)` (193-195).
3. Each `ValidationError` is caught (196). If it has a `code` that exists in the field's `error_messages`, its message is replaced with the field's custom message (197-198). Its `error_list` is added to a shared `errors` list (199).
4. After the loop, if any errors were collected, it raises a single `ValidationError(errors)` (200-201).

So validators don't stop at the first failure. All failing validators are reported together in one exception. I didn't see where `self.validators` is populated, because it wasn't in the retrieved source.

## 3. Where the exception goes
The exception propagates out of `Field.clean()` through `Field._clean_bound_field()` (`fields.py:271-273`). It reaches the `try` block in `BaseForm._clean_fields()` (`django/forms/forms.py:344-350`):
```python
except ValidationError as e:
    self.add_error(name, e)    # 349-350
```
Because the `except` is inside the per-field loop, one field's failure doesn't stop the other fields from being validated.

`add_error()` (`forms.py:264-316`) then stores the error:
- It takes `error.error_list` and keys it by the field name (296).
- If `field` isn't already in `self.errors`, it creates a new `self.error_class(renderer=..., field_id=self[field].auto_id)` in `self._errors[field]` (299-313). This `ErrorList` is stored in the form's `ErrorDict`.
- It calls `self._errors[field].extend(error_list)` (314), so every message from `run_validators` becomes an entry in that field's list.
- It deletes the field from `cleaned_data` if it was there (315-316).

## Where to read them
- `form.errors["fieldname"]` holds the combined list of validator messages for that field.
- `form.errors` is the same `_errors` dict (`forms.py:197-202`). `is_valid()` is false when it's non-empty.

## Subclasses that change the flow
Some field types override `clean()` and don't use this exact sequence. They are `FileField.clean` (`fields.py:681-700`), `ComboField.clean` (1043-1051), `MultiValueField.clean` (1099-1155) and `InlineForeignKeyField.clean` (`models.py:1407-1422`). I didn't read them, so I can't say how they raise errors. They still feed into the same `_clean_fields` handler.

# How a ModelForm builds, validates, and saves its instance

## 1. Entry
`ModelForm` is an empty subclass of `BaseModelForm` (`django/forms/models.py:585-586`). `is_valid()` follows the path from earlier, `is_valid → errors → full_clean` (`forms.py:204-206`, `197-202`, `324-339`). `full_clean` runs `_clean_fields`, `_clean_form` and `_post_clean` in order (`forms.py:337-339`). The model work happens in the `_post_clean` override.

## 2. `clean()` sets flags
`BaseModelForm.clean()` (`models.py:441-444`) sets `_validate_unique = True` and `_validate_constraints = True`, then returns `cleaned_data`. This runs in `_clean_form` (`forms.py:354`), before `_post_clean`.

## 3. `_post_clean()` builds and validates the instance
`models.py:479-513`

1. **Compute exclusions** with `_get_validation_exclusions()` (482, defined at 396-439). A model field is excluded from model validation when:
   - it isn't on the form (408-409);
   - `Meta.fields` or `Meta.exclude` leaves it out (414-417);
   - it already failed form validation (`field in self._errors`, 421-422);
   - it is blank on the form, not required there, and the model field disallows blank (430-438).
2. **Exclude inline FKs.** `InlineForeignKeyField` names are added to `exclude` (491-493). They stay in the uniqueness checks.
3. **Build the instance** with `construct_instance(self, self.instance, opts.fields, opts.exclude)` (496-498).
4. **Run model field validation** with `self.instance.full_clean(exclude=exclude, validate_unique=False, validate_constraints=False)` (502-505).
5. **Run uniqueness and constraint checks** separately (509-513). Both are gated by the flags from step 2:
   - `validate_unique()` (515-524) calls `instance.validate_unique(exclude=...)`.
   - `validate_constraints()` (526-535) calls `instance.validate_constraints(exclude=...)`.
   - Both recompute the exclusions first.

## 4. `construct_instance()` copies cleaned data onto the model
`models.py:50-93`

It loops over `opts.fields`. A field is skipped when:
- it is non-editable, an `AutoField`, or not in `cleaned_data` (62-67);
- it isn't in `fields`, or is in `exclude` (68-71);
- it has a model default, its value was omitted from the submitted data, and the cleaned value is empty (75-82). The default is kept instead of being overwritten.

`FileField`s are deferred (85-86). Other fields get `f.save_form_data(instance, cleaned_data[f.name])` (88). File fields are written afterwards (90-91), so a callable `upload_to` can see the other values.

The mutated `instance` is returned (93). Nothing is written to the database at this stage.

## 5. Where model errors land
Each model-level `ValidationError` goes through `_update_errors()` (`models.py:446-477`):
- The error is wrapped as an error dict, or as `NON_FIELD_ERRORS` if it has none (453-456).
- For each message, if its `code` has an override in the form field's `error_messages` (465-466), or in `Meta.error_messages[NON_FIELD_ERRORS]` for non-field errors (459-464), the message text is replaced (470-475). Errors for fields not on the form are skipped (467-468).
- It finishes with `self.add_error(None, errors)` (477). They end up in `form.errors` as described before.

`is_valid()` is therefore false if the form fields, the model's field validation, uniqueness or constraints produced any error.

## 6. `save(commit=True)`
`models.py:558-580`

1. It checks `self.errors` (564). If any exist, it raises `ValueError` saying the instance "could not be created/changed because the data didn't validate" (565-571). The word depends on `instance._state.adding`. Because `errors` is lazy, calling `save()` without `is_valid()` triggers validation here.
2. With `commit=True` (572-575):
   - `self.instance.save()` (574) writes the model row. I didn't read `Model.save`, so I can't describe its internals.
   - `self._save_m2m()` (575) then saves many-to-many data.
3. With `commit=False` (576-579), it only sets `self.save_m2m = self._save_m2m`, so the caller can save m2m data after saving the instance themselves.
4. It returns `self.instance` (580).

## 7. `_save_m2m()`
`models.py:537-556`

It iterates over `opts.many_to_many` plus `opts.private_fields` (548). It skips fields without `save_form_data` (549-550), fields outside `Meta.fields` (551-552), and fields in `Meta.exclude` (553-554). For the rest, if the name is in `cleaned_data`, it calls `f.save_form_data(self.instance, cleaned_data[f.name])` (555-556). This runs after the instance is saved because many-to-many rows need a primary key.

## Flow
```
is_valid() → full_clean()
  _clean_fields()   form fields → cleaned_data
  _clean_form()     BaseModelForm.clean(): set unique/constraint flags
  _post_clean()     exclusions → construct_instance → instance.full_clean
                    → validate_unique → validate_constraints
                    (errors via _update_errors → add_error)
save(commit)        errors? → ValueError
                    else instance.save() + _save_m2m()
```

# How field errors are rendered in templates

## 1. `{{ form.email.errors }}`
**Getting the errors.** `form.email` is a `BoundField`. Its `errors` property (`django/forms/boundfield.py:69-76`) returns `self.form.errors.get(self.name, ...)`. That is the field's `ErrorList` from the form's `ErrorDict`, which `add_error` filled earlier. If the field has no errors, it returns a fresh empty `form.error_class(renderer=...)` (74-76). The template can therefore always render it safely.

**Turning it into HTML.** The template engine calls `str()` or `__html__` on the `ErrorList`. Both are aliased to `render` in `RenderableMixin` (`django/forms/utils.py:57-58`):
```python
def render(self, template_name=None, context=None, renderer=None):
    renderer = renderer or self.renderer              # 52
    template = template_name or self.template_name    # 53
    context = context or self.get_context()           # 54
    return mark_safe(renderer.render(template, context))   # 55
```
The result is wrapped in `mark_safe`, so it isn't auto-escaped again. Escaping happens inside the error templates.

**Context.** `ErrorList.get_context()` (`utils.py:181-185`) returns `{"errors": self, "error_class": self.error_class}`.

**Templates.** `ErrorList` sets three template names (`utils.py:146-148`):
- `template_name = "django/forms/errors/list/default.html"`. This is the one used for `{{ form.email.errors }}`.
- `template_name_text`, the plain-text version.
- `template_name_ul`, used by `as_ul()`.

`list/default.html` (line 1) just includes `list/ul.html`. That template (line 1) renders:
```html
{% if errors %}<ul class="{{ error_class }}"{% if errors.field_id %} id="{{ errors.field_id }}_error"{% endif %}>{% for error in errors %}<li>{{ error }}</li>{% endfor %}</ul>{% endif %}
```
- Nothing is output if there are no errors.
- `error_class` defaults to `errorlist`. Non-field errors get `nonfield` (set in `add_error`, `forms.py:305-308`).
- The `id="<auto_id>_error"` attribute is there because `add_error` passes `field_id=self[field].auto_id` (`forms.py:310-313`).
- Each error is HTML-escaped by the template engine through `{{ error }}`.

**Renderer.** `renderer.render(...)` is `BaseRenderer.render` (`django/forms/renderers.py:27-29`). ## How `Field.clean()` runs the validators (`fields.py`)

`Field.clean()` is at `fields.py:203-211`. It runs three steps in order, and the first one that raises stops the rest:

1. `value = self.to_python(value)` (208) converts the raw input. The base version at 182-183 returns the value unchanged. Subclasses override it and raise `ValidationError` for bad input, with codes such as `invalid`.
2. `self.validate(value)` (209). The base version at 185-187 raises `ValidationError(self.error_messages["required"], code="required")` if the value is in `empty_values` and the field is required.
3. `self.run_validators(value)` (210) runs the validators in `self.validators`.

`run_validators` is at `fields.py:189-201`:
- It returns immediately for empty values (190-191), so validators like `max_length` never see `""` or `None`.
- It loops over every validator in `self.validators` (193-199), calling each as `v(value)`. These are the field's `default_validators` plus any passed in by the caller. A failing validator doesn't stop the loop, so all failures are collected.
- On a `ValidationError`, it first checks whether the error has a `code` that appears in the field's `error_messages` (197). If so, it replaces `e.message` with the field's message (198). This is how `Field(error_messages={"max_length": ...})` overrides a validator's default text.
- It then adds `e.error_list` to the `errors` list (199). `error_list` is the list of single-message `ValidationError`s inside the exception.
- After the loop, if there are any errors, it raises one combined `ValidationError(errors)` (200-201).

## Where the errors end up on the form (`forms.py`)

The `ValidationError` propagates out of `Field.clean()`, through `Field._clean_bound_field` (`fields.py:271-273`), and into `Form._clean_fields` (`forms.py:341-350`):

    if hasattr(self, "clean_%s" % name): ...                 # 346-348

A `ValidationError` from `clean_<name>()` is caught by the same handler. Because the assignment to `cleaned_data[name]` (345) never completes when `clean()` raises, a failed field never gets an entry.

- The error is already a `ValidationError`, so the wrapping at 282-285 is skipped.
- It has no `error_dict`, so line 296 builds `{name: e.error_list}`. That is where the `error_list` collected in `run_validators` is used.
