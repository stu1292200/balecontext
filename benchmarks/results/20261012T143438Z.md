# What `form.is_valid()` does

## 1. Entry point: `django/forms/forms.py:204-206`

```python
def is_valid(self):
    return self.is_bound and not self.errors
```

An unbound form returns `False` right away. For a bound form, the result depends on `self.errors`.

## 2. Lazy trigger: `errors` property, `forms.py:197-202`

`errors` runs `full_clean()` only if `self._errors is None`. Validation therefore runs once. Later calls to `is_valid()` or `.errors` reuse the cached `ErrorDict`.

## 3. Orchestrator: `full_clean()`, `forms.py:324-339`

1. Line 328 sets `self._errors = ErrorDict(...)`. This also marks the form as validated.
2. Lines 329-330 return early if the form is unbound.
3. Line 331 sets `self.cleaned_data = {}`.
4. Lines 334-335 return early if `empty_permitted` is set and `has_changed()` is false. `has_changed` (line 377) reads `changed_data` (line 381-383), which calls `BoundField._has_changed` for each field. Extra forms in a formset use this to skip validation.
5. Lines 337-339 run three phases in order: `_clean_fields()`, `_clean_form()`, `_post_clean()`.

## 4. Field validation: `_clean_fields()`, `forms.py:341-350`

For each `(name, bf)` from `_bound_items()` (lines 170-173):

1. Line 345 calls `field._clean_bound_field(bf)` and stores the result in `cleaned_data[name]`.
   - `_clean_bound_field` (`fields.py:271-273`) takes `bf.initial` if the field is disabled and `bf.data` otherwise. It then calls `Field.clean`.
   - `Field.clean` (`fields.py:203-211`) runs three steps:
     - `to_python` (182-183) coerces the raw value. The base class returns it unchanged, and subclasses override it.
     - `validate` (185-187) raises a `required` error if the value is in `empty_values` and the field is required.
     - `run_validators` (189-201) skips empty values. For the rest it runs every validator in `self.validators` and collects all failures instead of stopping at the first. If a validator's error `code` appears in the field's `error_messages`, it swaps in that custom message (197-198). It then raises one combined `ValidationError`.
2. Lines 346-348 look for a `clean_<name>()` method on the form. If one exists, it runs after the field's own cleaning, and its return value replaces `cleaned_data[name]`.
3. Lines 349-350 catch any `ValidationError` from either step and pass it to `add_error(name, e)`.

## 5. Error handling: `add_error()`, `forms.py:264-316`

- Lines 282-285 wrap a non-`ValidationError` in one.
- Lines 287-296 turn the error into a dict of `{field: error_list}`:
  - If it carries an `error_dict`, passing a `field` raises `TypeError` (289-292).
  - Otherwise the key is `field or NON_FIELD_ERRORS` (296). A `None` field puts the error under `__all__`.
- Lines 298-314 create the per-field `ErrorList` lazily. A field name that doesn't exist raises `ValueError` (300-304). Non-field errors get `error_class="nonfield"` (305-308).
- Line 314 extends the list.
- Lines 315-316 delete the field from `cleaned_data`, so only valid fields stay in it.

## 6. Form-wide cleaning: `_clean_form()`, `forms.py:352-359`

- Line 354 calls `self.clean()`. The default (`forms.py:368-375`) returns `self.cleaned_data`. Subclasses override it for cross-field checks.
- A `ValidationError` goes to `add_error(None, e)` (356). It lands in non-field errors, or you can pass a dict to attach errors to specific fields.
- If `clean()` returns something other than `None`, it replaces `cleaned_data` (358-359).

Because `_clean_form` runs after `_clean_fields`, `clean()` sees only the fields that passed. Code in `clean()` should use `.get()` for that reason.

## 7. Post-clean hook: `_post_clean()`, `forms.py:361-366`

The base implementation is a no-op (`pass`). `ModelForm` overrides it (`django/forms/models.py:479-513`):

- It builds the instance with `construct_instance` (496-498).
- It calls `instance.full_clean(exclude=..., validate_unique=False, validate_constraints=False)` (502-507). This is the model-level field validation. Both steps feed their errors back through `_update_errors`.
- `BaseModelForm.clean` (`models.py:441-444`) sets `_validate_unique` and `_validate_constraints` to `True`. That is why `validate_unique()` and `validate_constraints()` run at lines 510-513. If a subclass overrides `clean()` without calling `super()`, those checks are skipped.

## 8. Result

Back in `is_valid()`, `not self.errors` is true only when `_errors` is an empty `ErrorDict`. That means no field, `clean_<field>`, `clean()` or model-validation error was recorded.

# How `Field.clean()` runs validators, and where the errors go

## 1. `Field.clean()`: `django/forms/fields.py:203-211`

```python
value = self.to_python(value)        # 208
self.validate(value)                 # 209
self.run_validators(value)           # 210
return value                         # 211
```

The three steps run in sequence. An exception from `to_python` or `validate` aborts `clean()` immediately, so `run_validators` never runs in that case.

- **`to_python`** (`fields.py:182-183`) coerces the raw value. The base class returns it unchanged. Subclasses override it, for example `CharField` and `IntegerField`, and raise `ValidationError` for values they can't convert.
- **`validate`** (`fields.py:185-187`) raises `ValidationError(self.error_messages["required"], code="required")` if the value is in `empty_values` and the field is required.

## 2. `run_validators()`: `fields.py:189-201`

1. Lines 190-191 return at once for empty values. Validators such as `MaxLengthValidator` never see `""` or `None`.
2. Lines 192-199 loop over `self.validators` and call each one as `v(value)`:
   - A validator signals failure by raising `ValidationError`.
   - The loop catches the error and does not stop. Line 199 does `errors.extend(e.error_list)`, so every failing validator contributes.
   - Lines 197-198 handle message overrides. If the error has a `code` that is a key in the field's `error_messages`, `e.message` is replaced with the field's custom message.
3. Lines 200-201 raise a single `ValidationError(errors)` if anything was collected. This one exception carries the messages from all failing validators.

## 3. Where the exception goes: `django/forms/forms.py`

`Field.clean` is called from `_clean_fields` (`forms.py:341-350`), through `_clean_bound_field` (`fields.py:271-273`):

```python
try:
    self.cleaned_data[name] = field._clean_bound_field(bf)   # 345
    if hasattr(self, "clean_%s" % name): ...                 # 346-348
except ValidationError as e:
    self.add_error(name, e)                                  # 349-350
```

The `try` block also covers the form's `clean_<name>()` method. An error from it is handled the same way.

`add_error` (`forms.py:264-316`) then does the following:

- **Normalising** (lines 282-296): the exception is already a `ValidationError` with an `error_list` and no `error_dict`. Line 296 turns it into `{name: error.error_list}`.
- **Creating the container** (lines 298-313): if `name` isn't in `self.errors` yet, an `ErrorList` is created as `self._errors[name]`. It gets the `renderer` and `field_id=self[name].auto_id`.
- **Storing** (line 314): `self._errors[name].extend(error_list)`.
- **Cleaning up** (lines 315-316): if `name` is in `cleaned_data`, it is deleted. This only matters when `clean_<name>()` failed after `Field.clean` had already stored a value at line 345.

## 4. Final result

`self._errors` is the `ErrorDict` created in `full_clean` (`forms.py:328`), and it's what the `errors` property returns (`forms.py:197-202`). A failed field ends up as `form.errors[name]`, an `ErrorList` with one entry per failed validator, or one entry for a `required` or `to_python` failure.

`is_valid()` (`forms.py:204-206`) returns `False` because `self.errors` is non-empty. The failed field is absent from `cleaned_data`, so `Form.clean()` and `_post_clean()` only see fields that passed.

The coverage notes also list overrides of `clean()` in `FileField`, `ComboField`, `MultiValueField` and `InlineForeignKeyField`. I didn't read them, so they may run their validators differently from the base-class path above. I didn't modify any files.

# ModelForm: building, validating and saving the instance

## 1. Entry

`ModelForm` (`django/forms/models.py:585-586`) is an empty subclass of `BaseModelForm`. `is_valid()` follows the same path as before (`forms.py:204-206` → `errors` → `full_clean` at `forms.py:324-339`). The model-specific work happens in the `_post_clean` override.

## 2. Phase order inside `full_clean`

- `_clean_fields` runs the form fields (`forms.py:341-350`).
- `_clean_form` calls `BaseModelForm.clean` (`models.py:441-444`). It sets `_validate_unique` and `_validate_constraints` to `True` and returns `cleaned_data`.
- `_post_clean` (`models.py:479-513`) builds and validates the instance.

## 3. Building the instance: `construct_instance`, `models.py:50-93`

`_post_clean` calls `construct_instance(self, self.instance, opts.fields, opts.exclude)` at lines 496-498. For each model field it copies `cleaned_data` onto the instance with `f.save_form_data(instance, value)` (line 88). It skips a field when:

- the field is not editable, is an `AutoField`, or isn't in `cleaned_data` (62-67). This is why fields that failed form validation are skipped;
- it's outside `Meta.fields` or inside `Meta.exclude` (68-71);
- the model field has a default, the value was omitted from the submitted data, and the cleaned value is empty (75-82). The model default is kept in that case.

`FileField`s are deferred to a second loop (85-86, 90-91), so a callable `upload_to` can use the other fields' values.

A `ValidationError` from this step goes to `_update_errors` (`models.py:499-500`).

## 4. Validating the instance: `_post_clean`, `models.py:479-513`

1. **Compute exclusions** (line 482): `_get_validation_exclusions` (`models.py:396-439`) returns the fields to leave out of model validation. It excludes:
   - fields not on the form (408-409);
   - fields left out by `Meta.fields` or `Meta.exclude` (414-417);
   - fields that already failed form validation (421-422);
   - optional form fields that came in empty, when the model field is required and not `blank` (430-438). This stops a spurious model-level `required` error.

   Lines 491-493 also add `InlineForeignKeyField`s to the exclusions.
2. **Field validation** (lines 502-507): `self.instance.full_clean(exclude=exclude, validate_unique=False, validate_constraints=False)`. This is model field validation and `Model.clean()`, with uniqueness and constraint checks held back.
3. **Uniqueness and constraints** (510-513): if the flags set in `clean()` are true, it runs `validate_unique()` (`models.py:515-524`) and `validate_constraints()` (`models.py:526-535`). Each recomputes the exclusions, calls the matching instance method, and sends any `ValidationError` to `_update_errors`.

   If a subclass overrides `clean()` without calling `super()`, the flags are never set and both checks are skipped.

## 5. Where model errors go: `_update_errors`, `models.py:446-477`

- Lines 453-456 take `error_dict` if present. Otherwise they treat the whole error as non-field.
- Lines 458-475 replace each model-level message with the form's own message when the error `code` matches. The form's messages come from `Meta.error_messages` for non-field errors (459-464) or from the form field's `error_messages` (465-466). Errors for fields not on the form are skipped (467-468).
- Line 477 calls `self.add_error(None, errors)`. A dict error is spread across the matching fields, and anything else goes to `__all__` (see `add_error` at `forms.py:264-316`).

`is_valid()` returns `False` if any of these errors were recorded.

## 6. Writing it: `save()`, `models.py:558-580`

- **Guard** (564-571): if `self.errors` is non-empty, it raises `ValueError`. The message says "created" if `instance._state.adding` is true and "changed" otherwise.
- **`commit=True`** (572-575): `self.instance.save()`, then `self._save_m2m()`.
- **`commit=False`** (576-579): it attaches `self.save_m2m = self._save_m2m` so you can save the many-to-many data later, after saving the instance yourself.
- Line 580 returns `self.instance`.

`_save_m2m` (`models.py:537-556`) loops over `opts.many_to_many` and `opts.private_fields`. It skips fields without `save_form_data` (549-550), fields outside `Meta.fields` (551-552) and fields in `Meta.exclude` (553-554). For the rest, if the name is in `cleaned_data`, it calls `f.save_form_data(self.instance, cleaned_data[f.name])` (555-556).

M2M data is saved after the instance because the instance needs a primary key first.

# How form errors are rendered

## 1. `{{ form.email.errors }}`

**Getting the `ErrorList`.** `form.email` is a `BoundField`. Its `errors` property (`django/forms/boundfield.py:69-76`) returns `self.form.errors.get(self.name, <empty error_class>)`.

- `form.errors` is the lazily built `ErrorDict` (`forms.py:197-202`).
- `self.form.errors.get(self.name, ...)` triggers `full_clean()` if validation hasn't run yet.
- A field with no errors gets a fresh empty `ErrorList`, so the template never hits a missing key.
- `add_error` created the stored list with `renderer` and `field_id=self[field].auto_id` (`forms.py:310-313`). That `field_id` is used in the output.

**Turning it into HTML.** The Django template engine calls `str()` or `__html__` on the `ErrorList`. `RenderableMixin` (`django/forms/utils.py:45-58`) sets both to `render`:

```python
def render(self, template_name=None, context=None, renderer=None):  # 51
    renderer = renderer or self.renderer                            # 52
    template = template_name or self.template_name                  # 53
    context = context or self.get_context()                         # 54
    return mark_safe(renderer.render(template, context))            # 55
```

## How `Field.clean()` runs the validators

**Where the validator list comes from.** `Field.__init__` (`django/forms/fields.py:174`) builds the list as `[*self.default_validators, *validators]`. The class-level defaults (line 89) come first, then any passed to the constructor. Some subclasses append more. For example, `CharField` appends `MinLengthValidator` at line 286. `Field.__deepcopy__` copies the list per form instance (line 268).

**The call chain.**
- `Field.clean()` (`fields.py:203-211`) runs `to_python()`, then `validate()`, then `run_validators()`. The first exception stops the chain, so validators only run if the earlier steps passed.
- `validate()` (lines 185-187) raises the `required` error for empty values. It is a hook for subclass-specific checks.
- `run_validators()` (lines 189-201) works as follows:
  - It returns immediately if the value is in `empty_values` (lines 190-191). Validators never see empty input.
  - Each validator in `self.validators` is a callable that raises `ValidationError` on failure. It runs inside `try/except` (lines 193-196).
  - It doesn't stop at the first failure. For each failure it does two things:
    - If `e.code` is a key in `self.error_messages`, it replaces `e.message` with the field's custom message (lines 197-198). This is how `error_messages={"max_length": ...}` overrides a validator's default text.
    - It appends `e.error_list` to a shared `errors` list (line 199).
  - If anything was collected, it raises one `ValidationError(errors)` (lines 200-201).

**How the exception is structured.** `ValidationError.__init__` (`django/core/exceptions.py:147-188`) flattens a list of errors into a single `error_list` (lines 174-182). A single message sets `error_list = [self]` (line 188). That is why `run_validators` can combine several failures into one exception whose `error_list` holds one `ValidationError` per failed validator. A dict argument produces `error_dict` instead (lines 167-171), which is the form-wide case.

## Where the errors end up on the form

1. **Caught in `_clean_fields`** (`django/forms/forms.py:341-350`). Both the `field._clean_bound_field(bf)` call (line 345) and the `clean_<name>()` call (lines 346-348) sit inside one `try`. A `ValidationError` from either goes to `self.add_error(name, e)` (lines 349-350).
2. **Normalized in `add_error`** (`forms.py:264-316`).
   - A field-level error has an `error_list` and no `error_dict`, so it becomes `{name: error.error_list}` (line 296).
   - If `self._errors` has no entry for that field, `add_error` creates an `ErrorList` with `field_id=self[field].auto_id` (lines 310-313). It then extends the list with the individual `ValidationError` instances (line 314).
   - The final result is `form.errors[name]`, an `ErrorList` with one entry per failed validator. `ErrorList` and `ErrorDict` are in `django/forms/utils.py:141` and `:113`.
3. **Removed from `cleaned_data`.** `add_error` deletes the field from `cleaned_data` (`forms.py:315-316`). If `clean_<name>()` already ran and set a value, that value is dropped as well.
4. **Read back through the form.**
   - `form.errors` returns the `ErrorDict` (`forms.py:197-202`).
   - `form.has_error(name, code)` checks it, and the code lookup uses `as_data()` (`forms.py:318-322`). Each error keeps the `code` from the validator, which is why `has_error("f", "max_length")` works.
   - `bf.errors` is the same per-field entry, and `get_context` uses it for rendering (`forms.py:245`).

A validator error never goes to `__all__` (`NON_FIELD_ERRORS`). Only errors raised from `Form.clean()` land there, through `add_error(None, e)` at `forms.py:352-356`.
