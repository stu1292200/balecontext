## 2. Render time: `ExtendsNode.render` (`loader_tags.py:134-160`)

1. **Load the parent (line 135).**
   - `get_parent` (lines 117-132) resolves `parent_name` against the context.
   - An empty value raises `TemplateSyntaxError` (lines 119-125).
   - A `Template` object, or a backend wrapper with a `.template` attribute, is used directly (lines 126-131).
   - Otherwise `find_template` (lines 99-115) loads it by name.
2. **Avoid infinite recursion.**
   - `find_template` keeps a per-render history of origins in `render_context`, seeded with `self.origin` (lines 106-109).
   - It passes that list as `skip=history` to `Engine.find_template` (lines 110-113; `engine.py:155-163`). A template can therefore extend another template with the same name, such as an admin override extending the original.

3. **Get or create the `BlockContext` (lines 137-139).** It is stored in `context.render_context` under `BLOCK_CONTEXT_KEY`. `BlockContext` holds `blocks = defaultdict(list)`, a dictionary of FIFO queues (lines 15-17).
4. **Register the child's blocks (line 142).** `add_blocks` (`loader_tags.py:22-24`) does `insert(0, block)` for each block. Each new layer goes to the front of the list, and `pop()` takes from the end. The most-derived (child) block is therefore registered first, and it ends up at the end of the list, where `pop()` finds it first.
5. **Register the root's blocks (lines 144-155).**
   - It scans the parent's nodelist for the first non-`TextNode` (lines 146-148).
   - If that node isn't an `ExtendsNode`, the parent is the root template. All its `BlockNode`s are collected (lines 150-153) and added to the block context (line 154).
   - If the parent is itself an `ExtendsNode`, nothing is added here. Its own `render` call will register its blocks when it runs.
6. **Render the parent in the same context (lines 157-160).**

   - `NodeList.render` joins every node's rendered output into a `SafeString` (`base.py:1107-1108`).

Multi-level inheritance works by recursion. The child's `ExtendsNode` renders the parent. If the parent has its own `extends`, that `ExtendsNode.render` runs, adds its blocks behind the child's, and recurses up to the root.

## 3. Render time: `BlockNode.render` (`loader_tags.py:51-69`)

1. It fetches the `BlockContext` with `context.render_context.get(BLOCK_CONTEXT_KEY)` (line 52; `context.py:204-205`) and pushes a context scope (line 53).

## 1. Entry: `BaseForm.is_valid` (`django/forms/forms.py:204-206`)

`is_valid` returns `self.is_bound and not self.errors` (line 206). An unbound form is never valid. The `errors` property does the real work.

## 2. Lazy trigger: `BaseForm.errors` (`forms.py:197-202`)

- If `self._errors is None`, it calls `self.full_clean()` (lines 200-201). Validation therefore runs at most once per form and is cached in `_errors`.
- It returns the cached `ErrorDict` (line 202). `not self.errors` is true only when the dict is empty.

## 3. Orchestration: `BaseForm.full_clean` (`forms.py:324-339`)

1. It creates a fresh `ErrorDict` (line 328).
2. An unbound form stops here (lines 329-330).
3. It initializes `self.cleaned_data = {}` (line 331).
4. If `empty_permitted` is set and `has_changed()` is false, it returns early and skips all validation (lines 332-335). `has_changed` (`forms.py:377-379`) uses `changed_data` (`forms.py:381-383`). That runs `bf._has_changed()` per field, which the pack didn't follow (`django/forms/boundfield.py:150-165`).
5. Otherwise it runs three phases, in order:
   - `_clean_fields()` (line 337)
   - `_clean_form()` (line 338)
   - `_post_clean()` (line 339)

## 4. Field validation: `_clean_fields` (`forms.py:341-350`)

It loops over `self._bound_items()` (lines 342; `forms.py:170-173`), which yields each `(name, BoundField)` pair. For each field:

1. `field._clean_bound_field(bf)` (line 345; `django/forms/fields.py:271-273`):
   - It picks `bf.initial` for disabled fields, or `bf.data` otherwise (line 272).
   - It calls `self.clean(value)` (line 273).
2. `Field.clean` (`fields.py:203-211`) runs three steps in order:
   - `to_python(value)` (line 208). The base version returns the value unchanged (`fields.py:182-183`). Subclasses convert types here.
   - `validate(value)` (line 209). It raises `required` if the value is in `empty_values` and the field is required (`fields.py:185-187`).
   - `run_validators(value)` (line 210), covered in section 5.
3. The cleaned value is stored in `self.cleaned_data[name]` (line 345).
4. If the form defines `clean_<name>`, it is called and its return value replaces the stored value (lines 346-348).
5. Any `ValidationError` from steps 1-4 is caught and passed to `self.add_error(name, e)` (lines 349-350). The loop continues, so one bad field doesn't stop the others.

## 5. Validators: `Field.run_validators` (`fields.py:189-201`)

- Empty values skip the validators (lines 190-191).
- Each validator in `self.validators` runs. Its `ValidationError`s are collected rather than raised immediately (lines 193-199).
- If an error's `code` matches a key in the field's `error_messages`, the message is replaced with the field's custom one (lines 197-198).
- All collected errors are raised together as one `ValidationError(errors)` (lines 200-201). A field can therefore report several validator failures at once.

## 6. Error handling: `BaseForm.add_error` (`forms.py:264-316`)

- A non-`ValidationError` is wrapped in one (lines 282-285).
- The error is normalized into a `{field: error_list}` dict (lines 287-296):
  - If the error already has an `error_dict`, then `field` must be `None`. Otherwise it raises `TypeError` (lines 287-292), and the dict is used as is (line 294).
  - Otherwise the key is `field or NON_FIELD_ERRORS` (line 296).
- For each key (lines 298-316):
  - A key that is neither `NON_FIELD_ERRORS` nor a real field raises `ValueError` (lines 299-304).
  - It creates the `ErrorList` if needed (lines 305-313). Non-field errors use `error_class="nonfield"` (lines 306-308). Field errors get a `field_id` from `self[field].auto_id` (lines 310-313).
  - It extends the list with the new errors (line 314).
  - It removes the field from `cleaned_data` (lines 315-316). A field with errors therefore never appears in `cleaned_data`.
- `add_error` reads `self.errors` (line 299), which is already initialized at this point, so it doesn't re-enter `full_clean`.

## 7. Form-wide cleaning: `_clean_form` (`forms.py:352-359`)

- It calls `self.clean()` (line 354). The base `clean` returns `self.cleaned_data` (`forms.py:368-375`). This is the hook for cross-field validation.
- A `ValidationError` from `clean()` goes to `self.add_error(None, e)` (lines 355-356). That attaches it to `NON_FIELD_ERRORS`, which you read as `non_field_errors()`. If the error has an `error_dict`, it can target specific fields.
- If `clean()` returns something other than `None`, it replaces `self.cleaned_data` (lines 357-359).
- `clean()` runs even when some fields failed. It sees `cleaned_data` without the failed fields.

## 8. Post-clean hook: `_post_clean` (`forms.py:361-366`)

The base implementation is a no-op (`pass`, line 366). It is a hook for subclasses.

### Override for `ModelForm`

- `BaseModelForm.clean` (`django/forms/models.py:441-444`) sets `_validate_unique = True` and `_validate_constraints = True`, then returns `cleaned_data`.
- `BaseModelForm._post_clean` (`models.py:479-513`) does the model-level validation:

  - It copies the cleaned data onto the instance with `construct_instance` (lines 495-498).

  - Finally `validate_unique()` and `validate_constraints()` run if the flags from `clean()` are set (lines 509-513).

## 9. Result

Back in `is_valid` (line 206): the result is `True` only when the form is bound and `_errors` is empty after all three phases. `cleaned_data` then holds the validated values.

# How `Field.clean()` runs validators, and where the errors land

This draws on the code from my previous answer (BaleContext evidence). I didn't open or change any files. The overrides listed as not included (`FileField.clean`, `ComboField.clean`, `MultiValueField.clean` and others) aren't covered here, so this describes the base `Field` behavior only.

## 1. `Field.clean` (`django/forms/fields.py:203-211`)

```
value = self.to_python(value)     # 208
self.validate(value)              # 209
self.run_validators(value)        # 210
return value                      # 211
```

The steps run in sequence, and the first one to raise stops the rest:
- A `to_python` error means `validate` and `run_validators` never run.
- A `validate` error (for example `required`, at `fields.py:186-187`) means `run_validators` never runs.
- Only a value that passes both reaches the validators.

## 2. `Field.run_validators` (`fields.py:189-201`)

1. **Skip empty values** (lines 190-191). A value in `self.empty_values` returns immediately, so validators never see an empty value.
2. **Run every validator** in `self.validators` (lines 192-195). A failing validator doesn't stop the loop.
3. **Customize messages** (lines 196-198). Each caught `ValidationError` is checked: if its `code` is a key in the field's `error_messages`, its `message` is replaced with the field's own.
4. **Collect and flatten** (line 199). `errors.extend(e.error_list)` adds each error's list to the shared `errors` list.
5. **Raise once** (lines 200-201). If any error was collected, the method raises a single `ValidationError(errors)`. Several validator failures come out together as one exception.

## 3. Where the exception goes: `BaseForm._clean_fields` (`django/forms/forms.py:341-350`)

For each field, the code at lines 344-350 is:

```
try:
    self.cleaned_data[name] = field._clean_bound_field(bf)    # 345 → Field.clean (fields.py:271-273)
    if hasattr(self, "clean_%s" % name): ...                  # 346-348
except ValidationError as e:
    self.add_error(name, e)                                   # 350
```

- `_clean_bound_field` (`fields.py:271-273`) calls `self.clean(value)`. The exception propagates up to the `except` at line 349.
- The `try` block also covers any `clean_<name>()` method (lines 346-348). Its errors are caught and routed the same way.
- The loop continues to the next field, so errors accumulate across fields.

## 4. `BaseForm.add_error` (`forms.py:264-316`) stores them

- The error is normalized to `{name: error.error_list}` (line 296). Because `run_validators` already flattened its errors into one `ValidationError(errors)`, `error_list` contains every individual failure.
- On the first error for a field, an `ErrorList` is created and stored in `self._errors[name]` (lines 310-313). It carries `field_id=self[field].auto_id`.
- The errors are appended with `self._errors[field].extend(error_list)` (line 314).
- The field is removed from `self.cleaned_data` (lines 315-316), so a field that fails never appears in `cleaned_data`.

## 5. What this means for the form

`self._errors` is the `ErrorDict` created in `full_clean` (`forms.py:328`). `form.errors` returns it (`forms.py:197-202`), and `is_valid()` is `is_bound and not self.errors` (`forms.py:206`). So one validator failure on one field makes `is_valid()` return `False`, and the messages sit under `form.errors[name]`.

## Flow

```
Field.clean            fields.py:203
 ├ to_python           :208   raises → skip the rest
 ├ validate            :209   raises (e.g. required) → skip run_validators
 └ run_validators      :210   collects all failures → one ValidationError(errors)
       ↓ propagates up through _clean_bound_field (fields.py:273)
BaseForm._clean_fields forms.py:349-350   except ValidationError → add_error(name, e)
       ↓
BaseForm.add_error     forms.py:296, 310-316   → self._errors[name] (ErrorList); drop from cleaned_data
```

## 2. Render time: the block registry

- `pop` takes the last entry (`:26-30`).
- `push` appends (`:32-33`).

## 3. Rendering a child template's `{% extends %}`

Rendering starts at `Template.render` (`base.py:169-177`). It pushes a render-context state (`:171`), binds the template if needed (`:172-175`), and calls `_render`, which calls `self.nodelist.render(context)` (`:166-167`). **`ExtendsNode.render`** (`loader_tags.py:134-160`):
1. **Find the parent:** `get_parent` (`:117-132`) resolves the name. It returns a `Template` as it is, or the `.template` attribute of a backend wrapper (`:126-131`). Otherwise it calls `find_template` (`:132`).

2. **Create the `BlockContext`** if it does not exist yet (`:137-139`).
3. **Register the child's blocks:** `block_context.add_blocks(self.blocks)` (`:142`).
4. **Register the root's blocks:** it scans the parent's nodelist for the first non-text node (`:146-155`). If that node is not an `ExtendsNode`, the parent is the root, and its blocks are added (`:149-154`). If the parent also extends, it registers its own blocks when its `ExtendsNode.render` runs.

5. **Render the parent:** `compiled_parent._render(context)` (`:159-160`) is called directly under `push_state(compiled_parent, isolated_context=False)` (`context.py:210-221`). That keeps the same parser context and the same render-context scope, so `block_context` is shared.

Chains of any depth work the same way: each `ExtendsNode` adds its blocks and then renders its parent, until the root template renders with all the overrides registered.

## 4. Rendering `BlockNode` (`loader_tags.py:51-69`)

- It looks up `block_context` in the render context (`:52`) and opens `context.push()` (`:53`).
- **No `block_context`** (a standalone template, or the root rendered directly) (`:54-56`): it sets `context["block"] = self` and renders its own nodelist.
- **With `block_context`** (`:57-68`):
  - `block_context.pop(self.name)` takes the most-derived override (`:58`). If there is none, it uses itself (`:59-60`).
  - It copies the node (`:63`) and stores `block.context = context` (`:64`). The comment says this is for thread safety, since the original node is shared across renders.
  - It sets `context["block"] = block` (`:65`) and renders the chosen nodelist (`:66`).
  - It pushes the popped block back (`:67-68`), so later renders of the same block name, such as the same block inside a `{% for %}` loop, see it again.

## 5. `{{ block.super }}`

`BlockNode.super` (`loader_tags.py:71-83`):
- It raises `TemplateSyntaxError` if the node has no `context`, for example when it is used in a base template (`:72-76`).
- If the registry still holds another block of that name, it returns `mark_safe(self.render(self.context))` (`:78-82`). That pops the next entry down the stack, which is the parent's version, and renders it. Otherwise it returns `""` (`:83`).

## 1. Where the validators come from

- `Field.default_validators = []` (`django/forms/fields.py:89`) is a class-level default that subclasses override.
- `Field.__init__` builds the instance list as `self.validators = [*self.default_validators, *validators]` (`fields.py:174`). The second part is the `validators=` keyword argument (`:108`).
- Field subclasses append validators for their options:
  - `CharField` adds `MinLengthValidator` and `MaxLengthValidator` (`fields.py:286-288`) and `ProhibitNullCharactersValidator` (`:289`).
  - `IntegerField` adds `MaxValueValidator`, `MinValueValidator` and `StepValueValidator` (`:327-332`).
  - `DecimalField` adds `DecimalValidator` (`:419`).
- `__deepcopy__` copies the list per form instance (`:268`).

## 2. `Field.clean` (`fields.py:203-211`)

```python
value = self.to_python(value)
self.validate(value)
self.run_validators(value)
return value
```

The steps run in a fixed order, and any step can raise `ValidationError`. A failure in `to_python` or `validate` stops the chain, so `run_validators` never sees that value.

## 3. `run_validators` (`fields.py:189-201`)

1. If the value is in `empty_values`, it returns without running any validator (`:190-191`).
2. It loops over `self.validators` (`:193`) and calls each as `v(value)` (`:195`). A validator signals failure by raising `ValidationError`.
3. It catches each error and does not stop at the first one (`:196`).
   - If the error has a code that is also a key in the field's `error_messages`, it replaces the message with the field's version (`:197-198`). This is how `error_messages={"max_length": "..."}` on a field overrides the validator's default text.
   - It collects `e.error_list` (`:199`).
4. If anything was collected, it raises one `ValidationError(errors)` (`:200-201`), so all validator failures for the field are reported together.

## 4. How the `ValidationError` is shaped

`ValidationError.__init__` (`django/core/exceptions.py:147-188`) normalises its input:
- A plain message becomes a leaf with `message`, `code` and `params`, and `error_list = [self]` (`:184-188`).
- A list is flattened into `self.error_list`, with each element wrapped as a `ValidationError` (`:173-182`).
- A dict becomes `error_dict`, mapping field name to `error_list` (`:166-171`).

Iterating it yields formatted strings, applying `message %= params` (`:212-221`).
